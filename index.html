Notification history usage report「通知履歴」機能 利用状況レポート

Search Array · production · as of 2026-10-23 · corrected 2026-10-30サーチアレイ・本番環境・2026-10-23 時点（2026-10-30 訂正）

There is no usage logging for the notification bell. Opening the notification panel is not recorded as usage — no user, no database row, no click-log entry — so open counts and open rates cannot be produced for any period, past or present. What is recorded — in the database, not in logs — is one row per user per notification at the moment they open it. That gives us click counts, click rates, usage over time and usage by notification type, for the whole life of the feature. 通知ベルには利用ログが実装されていません。ユーザーが通知一覧を開いても、利用データとしては記録されません（ユーザー・DBレコード・クリックログのいずれも残りません）。そのため開封数・開封率は過去分を含め取得できません。一方でデータベース側には、ユーザーが個別の通知を開いた時点で既読レコードが1件ずつ記録されています。これによりクリック数・クリック率・期間別および通知の種類別の利用状況を、機能リリース時点まで遡って集計できます。

What was measured計測対象

  • Opening a notification (click). The user taps an item in the list and its detail opens. This writes a read receipt, and it is the one user action the system records.
  • Eligible audience. The users who could have seen a given notification as new — those who registered before it was published. A notification published before a user joined is shown to them already-read and never counts toward their bell badge, so they are excluded from the denominator of every rate. They are not prevented from opening it: the item is still in their list, and 347 of the opens below (3.9%, by 285 users) are exactly that. Those opens count as usage but are excluded from the numerator, so the numerator stays a subset of the denominator.
  • Counting. A receipt is written only on the first open and is never updated. Every figure here is unique users, not views; re-reads are invisible.
  • Measurement window. The feature is gated by a build-time flag, so the period covered is not the code's merge date (mid-July 2026) but the period the flag was live in a production build. That period is taken from the data itself — the earliest read receipt and the earliest published notification — not from a configuration file.
  • 通知を開く（クリック）。一覧の項目をタップして詳細を開く操作です。このとき既読レコードが書き込まれ、これがシステムの記録している唯一のユーザー操作です。
  • 対象ユーザー。その通知を未読として見られる状態だったユーザー、すなわち公開前に登録していたユーザーです。登録前に公開された通知は既読扱いで表示され、ベルの未読件数にも加算されないため、利用率の分母から除外しています。ただし非表示ではなく、一覧から開くことは可能です。実際、以下の開封のうち 347 件（3.9%・285名）がこれに該当します。これらは利用回数には含めますが、分子が分母の部分集合であるよう、利用率の分子からは除外しています。
  • 集計方法。既読レコードは初回のみ記録され更新されません。したがって各数値はユニークユーザー数であり閲覧回数ではありません。再読は記録されません。
  • 集計期間。本機能はビルド時に決まるフラグで制御されているため、対象期間はコードのマージ時期（2026年7月中旬）ではなく、本番ビルドでフラグが有効になっていた期間です。この期間は設定ファイルの値ではなく、最も古い既読レコードと最も古い通知の公開日からデータ側で確認しています。

A note on the denominator分母についての補足

The headline rate above is measured against all 29,654 registered accounts, which is the conservative reading — most of those accounts are dormant. Measured against the users actually active in the same period, the picture is very different.上記の利用率は全登録アカウント 29,654 件を分母とした、最も控えめな見方です。登録アカウントの多くは休眠状態であり、同じ期間に実際に利用していたユーザーを分母にすると見え方は大きく変わります。

Appendix — the other two notification channels付録：その他2つの通知チャネル

These are separate features from the bell, with their own records. Do not read these figures as bell usage. They are here because they are the only places in the product where the open-rate question has an answer.いずれもベルアイコンとは別機能であり、記録の仕組みも異なります。以下をベルの利用状況として読まないようご注意ください。「開封率」に数値で答えられるのはこの2つだけであるため、参考として記載します。

A. Browser push notifications (FCM)A. ブラウザのプッシュ通知（FCM）

Delivered means accepted by FCM, not opened. Per-device results are not stored, and push clicks exist only as anonymous log lines with ~14-day retention, so no open or click rate can be computed for push.「配信成功」はFCMが受け付けた件数であり、開封された件数ではありません。端末ごとの結果は保存されておらず、プッシュのクリックはユーザーIDを含まないログ（保持期間約14日）にしか残らないため、プッシュの開封率・クリック率は算出できません。

B. Game notification emailB. ゲーム通知メール

This is the one true open rate in the product. Opens are measured by a tracking pixel in the email and recorded once, on the first open. Mail clients that block images are not counted, so every rate here is a lower bound.製品内で唯一、本当の意味での開封率を計測しているのがこのチャネルです。開封はメール内のトラッキング画像で計測し、初回のみ記録されます。画像を読み込まないメールソフトでは計測されないため、開封率は下限値です。

Data that could not be collectedログから取得できなかったデータ

This is the substance of the investigation, and most of the requested examples fall here.本調査の中心となる部分です。ご提示いただいた例の多くがここに該当します。

  • Opening the notification panel is not recorded as usage. Tapping the bell writes nothing to the database and no usage-log entry. It only loads the notification list, which leaves an anonymous line in the server access log — no user, kept ~14 days (see the last point). How many users opened the panel, and how often, cannot be known — now or retroactively. "Open count / open rate" as described cannot be produced.
  • Click-through rate in the strict sense is unavailable. It would be clicks ÷ panel opens, and that denominator does not exist. The rate reported above is a different and more useful one: users who opened a notification ÷ users who could have seen it.
  • Repeat opens are not recorded. The receipt is written once and never updated, so a user who reads a notification ten times counts once, and the last-read time is unknown.
  • There is no delivery or impression record. Nothing records that a notification was shown in a user's list, so "open rate" in the push-notification sense does not apply to this feature.
  • Tag filtering, scrolling and dismissals are not recorded.
  • None of the existing click logs covers the bell. The [game click] log records only its own list of actions (配列, 検索, カードリスト and similar) and has no notification entry. The fake-click log records only taps on the 「詳細」 button. Checked against the code and by tapping the bell on 2026-10-30: neither fires.
  • A similarly named log exists but belongs to a different feature. [Notification Click Track] in the production logs records clicks on browser push notifications (FCM), not the bell. It is also anonymous — that endpoint requires no login — so it carries no user id. It must not be read as bell data.
  • Google Analytics cannot fill the gap, even retroactively. GA4 is installed site-wide, but the site sends no custom events at all, and the panel is an overlay rather than a page, so GA4 never recorded even a page view for it.
  • No archived log helps. All 35 retained production log files were searched in full, including the compressed archives: zero notification entries. Log retention is about 14 days in any case.
  • The server access log cannot stand in for the missing panel-open count. Estimating panel opens from requests to the notification list endpoint was considered and rejected: the access log carries no user id (logging runs before authentication), so it cannot be reduced to users; retention is only ~14 days, so it says nothing about the past; the collector double-counts by roughly 14%; and the list endpoint is paged by infinite scroll, so one panel open produces an unpredictable number of requests. A number derived this way would be wrong in an unknown direction, and is not reported.
  • 通知一覧を開く操作は、利用データとして記録されていません。ベルをタップしてもDBにも利用ログにも何も残りません。一覧の読み込みに伴い、サーバーのアクセスログに匿名の1行（ユーザー不明・保持期間約14日）が残るのみです（最後の項目を参照）。何人が何回一覧を開いたかは、現在も過去分も把握できません。ご要望の「開封数・開封率」は取得できません。
  • 厳密な意味でのクリック率は算出できません。本来はクリック数÷一覧の開封数ですが、分母が存在しません。上記の利用率はこれとは異なる、より実態に近い指標です：通知を開いたユーザー数 ÷ その通知を見られる状態だったユーザー数。
  • 再読は記録されません。既読レコードは初回のみ記録され更新されないため、同じ通知を10回読んでも1回として数えられ、最終閲覧日時も分かりません。
  • 配信・表示の記録がありません。通知が一覧に表示されたという記録は残らないため、プッシュ通知でいう「開封率」の概念はこの機能には適用できません。
  • タグによる絞り込み・スクロール・閉じる操作も記録されていません。
  • 既存のクリックログもベルには対応していません。[game click] ログは定義済みの操作（配列・検索・カードリストなど）のみを記録し、通知の項目はありません。フェイククリックのログは「詳細」ボタンのタップのみを記録します。コード確認と、2026-10-30 に実際にベルをタップして確認しました。いずれも記録されません。
  • 名称の似たログがありますが別機能のものです。本番ログの [Notification Click Track] はブラウザのプッシュ通知（FCM）のクリック記録であり、ベルアイコンのものではありません。また当該エンドポイントは認証不要のためユーザーIDも含まれません。ベルの利用データとして扱わないようご注意ください。
  • Google Analyticsでも補完できません（過去分も同様）。GA4はサイト全体に導入されていますが、カスタムイベントを一切送信しておらず、通知一覧はページ遷移ではなくオーバーレイ表示のため、ページビューすら記録されていません。
  • 保存済みログにも該当データはありません。保管されている本番ログ35ファイルを圧縮分も含めて全文検索しましたが、通知関連の記録は0件でした。そもそもログの保持期間は約14日です。
  • サーバーのアクセスログで開封数を代替することもできません。通知一覧APIへのリクエスト数から開封数を推定する方法も検討しましたが採用しませんでした。アクセスログにはユーザーIDが含まれないため（ログ出力が認証処理より前に実行される仕様）ユーザー単位に集計できず、保持期間は約14日のため過去分は分からず、収集側の二重計上で約14%多く出て、さらに一覧APIは無限スクロールでページングされるため1回の開封で何回リクエストが発生するか特定できません。この方法の数値は誤差の方向すら分からないため記載しません。

Notes for the dev team開発チーム向けメモ

  • Verified absence, not an assumption. The shared user-action tracking system has a registry of tracked actions kept in sync in two places, and neither contains any notification entry. The notification API handlers log only on error. None of the five notification UI components calls a tracking function. The analytics events table exists, but its only writer is search.
  • To make this measurable, reuse the analytics events table rather than adding a new one. It was built for reuse, it already has its own Postgres box, and its properties JSONB column is the intended extension point and is currently unused. Suggested events: announcement_panel_open, announcement_item_click (notification id and tags in properties), announcement_tag_filter.
  • Do not solve this with a log line. Adding a log statement would be quicker, but logs are kept only ~14 days, so the history would evaporate — the same problem flagged in the previous (検索履歴) report. Write events to the database.
  • This should be raised as its own ticket.
  • 推測ではなく確認済みの「存在しない」です。共通のユーザー行動計測には計測対象アクションの一覧が2箇所に同期して定義されていますが、通知関連の項目はどちらにもありません。通知APIのハンドラはエラー時のみログを出力し、通知UIの5つのコンポーネントはいずれも計測関数を呼んでいません。analytics の events テーブルは存在しますが、書き込んでいるのは検索機能のみです。
  • 計測可能にするには、新規テーブルではなく analytics の events テーブルを再利用してください。同テーブルは再利用を前提に設計され、専用のPostgreSQLも既にあり、拡張用の properties JSONB カラムは未使用のままです。想定イベント：announcement_panel_open、announcement_item_click（properties に通知IDとタグを格納）、announcement_tag_filter。
  • ログ出力で済ませないでください。ログ追加のほうが早いですが、保持期間が約14日のため履歴が消えます。前回（検索履歴）レポートで指摘したのと同じ問題です。DBにイベントを保存してください。
